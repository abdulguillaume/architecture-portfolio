Most recent project

Proposal Evaluator — Human-in-the-loop RFQ scoring

Role: Sole builder / Solution Architect

Open source: github.com/abdulguillaume/ProposalEvaluation

Context

A combined-method RFQ (technical 70% / financial 30%) often arrives as email attachments and shared folders — for this POC, about 21 vendor packs and three staff evaluators. Each bid meant reading the full offer against a long TOR, scoring the same criteria, and keeping a ranking that would stand up in committee.

That first pass is slow and hard to keep consistent. People should own setup, challenge, and approval — not reread twenty methodology PDFs. The system drafts technical scores; it does not replace the evaluation committee.

This share is a POC: authentication and authorization are not in scope. Whoever creates the RFQ can add agents and can approve or reject agent summaries and scores — there is no separate evaluator role or login gate yet.

Cost impact

Almost all variable API cost is the LLM — for this ~21-vendor RFQ, a full technical first pass on gpt-4o-mini is on the order of $1–$4. The larger saving is staff time: without the system, three evaluators doing a first full read can mean tens of hours (e.g. ~1 hour per pack × 21 × 3). With it, agents draft summaries and scores; people skim and accept or reject — hours of gated review instead of first-reading every pack.

High-level architecture

The application owns the facts (RFQ, vendor profiles, files, jobs, summaries, scores). Narrow agents run late, only after a person requests evaluation, with a prepared prompt and job-scoped tools. People stay on the gates: accept/reject the summary, then accept/reject scores. The app computes TWS, pass/fail, and rank — agents never do the math.

  • Web app — intake, review UI, APIs, deterministic ranking
  • Agent host — model + tool loop (summary agent, scoring agent)
  • MCP — thin adapter over app APIs; model swappable (OpenRouter, Groq, Azure OpenAI)

Agentic workflow

Staff load the RFQ and vendor packs; agents draft a summary then scores; evaluators accept or reject at each gate. Ranking stays in the application.

Tradeoffs

App owns totals; agents draft scores

Why
Same formula for every vendor; no model arithmetic errors on weighted totals.
Cost
Agents cannot “just give a total”; tool failures must be visible in the job.

Two agents + summary gate

Why
Cheap to stop a non-responsive bid before scoring; scoring uses one accepted brief.
Cost
Two model runs per accepted vendor and more review clicks.

Consistency over autonomy

Why
Prepared prompts, tools over SQL, and human accept/reject fit real procurement review.
Cost
Slower at the keyboard than a “score the folder” bot — safer in a committee file.

BidAgent — Infrastructure Bid Desk

Role: Sole builder / Solution Architect

Overview

Proof-of-concept multi-agent bid desk for Miami-area public procurement. Built for a small technology / low-voltage contractor (Arimex Consulting LLC) to find and screen Phase 1 packages (~$10k–$100k) without chasing large civil primes.

Multi-agent bid desk that discovers Miami-area public tech/electrical packages, screens compliance, and drafts a human-approved bid packet — without ever submitting to the portal.

Business challenge

  • Public ITBs and RFQs are scattered across agency portals
  • Reading packages and checking licenses, insurance, and vendor registration is slow and easy to get wrong
  • Automation helps, but bids must stay human-approved — nothing should auto-submit to a government portal

What I built

A full Discover → Evaluate → draft packet workflow:

Discover

  • Live shortlist from Miami-Dade StratProc, City of Miami BidNet Direct, and related Florida BidNet purchasing-group listings
  • Clear notices where portals are login-walled

Evaluate

  • Upload PDF/DOCX/text solicitations
  • Extract requirements; run compliance against a contractor profile
  • Score bid/no-bid with hard stops for missing license, COI, or vendor registration

Go path

  • Work packages and labor-hour estimate buildup from a price book
  • Risk register and draft strategy packet
  • Packet stays non-final until a human approves

Bid Desk UI

  • Browser client for Discover, Evaluate, Jobs, and company profile / labor rates
  • Never auto-submits to agency portals

Agentic workflow

Discover opportunities, evaluate solicitations, estimate and draft a packet, then require human approval before anything is treated as bid-ready. Nothing auto-submits to agency portals.

Key architectural decisions

LLM for reading; code for money

Challenge
Agents must extract requirements and reason about compliance without becoming the system of record for dollars.
Decision
Azure OpenAI for structured agent outputs; deterministic C# for markup math and labor-hour pricing.
Outcome
Readable solicitations and scored recommendations, with pricing that stays auditable and policy-bound.

Safety-first bidding

Challenge
Regulated public procurement must not allow accidental or automated portal submission.
Decision
Hard stops for missing license/COI/registration; packet approval only marks the draft as human-approved; no agency portal submit.
Outcome
Automation accelerates screening while a human remains accountable for the bid decision.

Real portal integration

Challenge
Public sources are uneven: some are open, others login-walled.
Decision
Composite opportunity search and solicitation fetchers for Miami-area sources, with honest notices where access is blocked.
Outcome
A usable shortlist grounded in live portals — not only mocks.

Scope focus

Practical Phase 1 scope: structured cabling, CCTV, access control, network, building technology, and electrical-tech packages.

Technology landscape

  • .NET 9 / ASP.NET Core
  • SQL Server
  • Azure OpenAI
  • Static Bid Desk (HTML/CSS/JS)
  • Stored procedures & paged lists
  • Portal adapters (Miami-area)

BRaVe — Biometric Registration & Verification System

Role: Lead Solution Architect & Technical Lead

Overview

BRaVe is a multi-tenant biometric registration and verification platform supporting beneficiary registration, verification, targeting, referrals, and biometric matching workflows. I serve as the architecture owner and technical lead, working directly with the Product Owner and leading a team of three software developers.

Scale

Growth shape

Strong volume in 2023, a dip in 2024, and a peak in 2025 when IOM Chad was onboarded as a tenant and started using the system. 2026 is partial-year only (through July) — not comparable to full prior years.

Open source & digital public good

BRaVe began as an internal platform and was released as open source in June 2026. The work sits in a programme partly funded by ECHO, within a broader interoperability effort across registration systems used by humanitarian partners. The intent is to offer BRaVe as a digital public good that other organizations can adopt and extend.

Source and documentation: github.com/bravesystem.

Deployment & environments

The platform is deployed across four Azure resource-group sets that we operate:

  • Internal — Dev, UAT, and Prod for our own delivery and operations
  • Partner resource group for partners who do not yet run their own system

We manage both the internal and partner estates. Production and the partner environment remain on separate resource groups so that data governance boundaries stay clear, as directed by headquarters.

Business challenge

Design a secure and scalable platform capable of:

  • Managing multiple organizations on a single platform
  • Supporting biometric registration and matching
  • Supporting field data collection via mobile that works offline and syncs to the server when online, alongside web access
  • Supporting AI-assisted targeting and referrals
  • Maintaining strict data isolation between tenants

Fourth project

BRaVe Legacy — Offline field registration platform

Role: Lead Software Developer / System Architect

Overview

BRaVe Legacy is a fully offline biometric registration system for field operations. Each field site collects and checks data locally. Sites periodically exchange data with a central server so registrations can be consolidated and duplicates can be found across sites.

The design balances disconnected field reality with headquarters-level integrity: collect and match offline, consolidate centrally for cross-site deduplication, then push differentials back to the field.

Data collection preview

South Sudan and Nigeria missions. Latest registration recorded: 5 February 2026 (South Sudan), November 2025 (Nigeria).

Year Beneficiaries Individuals
2018 (SS) 133,863 433,661
2019 463,952 1,766,327
2020 41,943 141,841
2021 75,494 332,102
2022 85,277 392,411
2023 68,080 272,564
2024 56,277 208,448
2025 46,109 178,625
2026 (SS through Feb) 2,975 11,444

Scale

Cumulative across both missions: 975k beneficiary records and 3.72M individuals (South Sudan: 344k / 1.22M; Nigeria: 631k / 2.50M).

Growth shape

Each mission peaked during initial large-scale rollout — South Sudan in 2018, Nigeria in 2019 — then moved to lower sustained volumes. Nigeria collection ended in November 2025; South Sudan continued into early 2026 (partial year only — not comparable to full prior years).

Business challenge

  • Operate registration with little or no connectivity in the field
  • Support fingerprint capture and fast local duplicate checks
  • Consolidate many field sites into one central picture
  • Detect cross-site duplicates when people register at more than one location
  • Keep field databases and matching stores aligned via periodic differentials

Field operations

Each site runs a field operations server (SQL Server + licensing), a Debian biometric matching server (Neurotechnology), and data-entry laptops with 4-4-2 fingerprint scanners. On save, the client updates the local database, checks licensing, runs a local duplicate check, and copies biometrics into the matching store.

Central server

Central hosts SQL Server, a matching server, and a consolidation service that picks up field backups from a shared drive, writes them to the central database, and pushes biometrics into central matching for cross-site deduplication. An admin client can then produce a differential dump for a given period.

Data consolidation loop

End of day: the field creates a backup of new and updated registrations and drops it on the inbound share. Central consolidates, then an admin publishes a differential. Field teams download and apply it to update both the local database and matching server.

Key architectural decisions

Fully offline field operation

Challenge
Field sites often have unreliable or no connectivity.
Decision
Run complete local stacks: SQL Server, licensing, and biometric matching on site.
Outcome
Registration and local deduplication continue without continuous network access.

Dedicated matching appliance

Challenge
Many-to-many biometric search must stay fast at large template counts.
Decision
Deploy Neurotechnology matching on a separate Debian server per site and at central.
Outcome
Sub-2s matching even around one million templates, without blocking the SQL path.

File-based consolidation

Challenge
Move data between disconnected sites and headquarters safely.
Decision
Use shared-drive backups inbound and differential dumps outbound, processed by a central service.
Outcome
Clear operational rhythm without requiring always-on site connectivity.

Cross-site deduplication

Challenge
People may register at site X and later again at site Y.
Decision
Push consolidated biometrics into a central matching store after each import.
Outcome
Duplicates can be detected across field operations, not only within one site.
